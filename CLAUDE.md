# PS Tracker — контекст проекта

Сайт-трекер игр PlayStation. Сейчас один пользователь (Артём), без регистрации. В Фазе 20 (решение Артёма 2026-10-29): несколько пользователей по белому списку, у каждого своя коллекция PSN; владелец — Артём.
Референсы UI: `docs/reference/collection-reference.png` (коллекция), `docs/reference/themes-overview.png` (7 тем на одном наборе токенов).

## Цель MVP
1. Ежедневный синк с PSN: игры, часы, трофеи, дата последнего запуска.
2. Коллекция: карточки, поиск, фильтры, ручная смена статуса.
3. Статистика: часы, пройдено/брошено по месяцу и году, жанры, трофеи.
4. Итоги года (Wrapped): сторис-слайды в браузере, выбор года.
5. Бэклог: игра со статусом `backlog` попадает в список.

Вне MVP: Xbox/Switch/PC, шэринг-картинок, IGDB, открытая регистрация. Мультипользовательность по белому списку вошла в Фазу 20, интерактивный тур по сайту — в Фазу 21.
Решение Артёма 2026-11-02: игры вне библиотеки PSN добавляются вручную через поиск RAWG (Фаза 43 — бэклог с пометкой «не куплено», Фаза 44 — пройденные на других платформах); синк с Xbox/Nintendo не делаем (нет публичного API), такие игры не попадают в Статистику и Итоги.
Вкладка «План» (роадмап бэклога на год) вошла в Фазу 12. «Подскажи» (Фаза 13): скоринг игр бэклога по истории, бесплатный LLM (free tier, ключ `LLM_API_KEY` на сервере) только формулирует причину, без платных моделей; вкладка «У тебя нет» (Фазы 30–31): кандидатов выбирает RAWG по правилам (PS5/PS4, топ-жанры, рейтинг), LLM только формулирует причину (при сбое шаблон), игр из библиотеки в выдаче нет. Внешний каталог новинок и дат релиза: RAWG (для планируемых игр и подтверждения советов «Новое от ИИ», ключ `RAWG_API_KEY` на сервере, на экране ссылка-атрибуция). Жанры по-прежнему только из PSN.

## Зафиксированные решения
- Только PSN. Интерфейс только RU. До Фазы 20 один пользователь; с Фазы 20 — пользователи из белого списка (роли `owner | member`), у каждого свои данные (`user_id` во всех пользовательских таблицах), запрос без фильтра по пользователю — баг.
- Фаза 41 (решение Артёма 2026-11-01): отход от «один вход = один пользователь». К одному входу (почте) привязано до 3 PSN-профилей; каждый профиль — отдельная строка `allowed_users` (`user_id`), дополнительные ссылаются на основной через `primary_user_id`. Данные по-прежнему изолированы по `user_id`; активный профиль в сессии (`pid`) проверяется на принадлежность входу при каждом запросе. Лимиты RAWG/HLTB/LLM — на профиль. Telegram-сводка — только по основным профилям. Отвязанный профиль 30 дней лежит в архиве.
- Статусы: `playing | completed | dropped | backlog | shelved`, плюс «без статуса» (новая игра после синка).
- Иконки статусов из референса: △ играю, ○ пройдено, □ бэклог, ✕ брошено. Для `shelved` иконку выбирает designer. Фигуры только для статусов, логотип текстовый.
- `completed_at` / `dropped_at` = дата последнего запуска игры в момент смены статуса. Дальше правится вручную.
- Часы за период считаем по ежедневным снимкам `playtime_snapshots` (PSN даёт только суммарные часы). До первого синка истории часов нет.
- Трофеи за период считаем по `earned_at` (история полная).
- Жанры только из того, что отдаёт PSN (`concept.genres`, есть у всех игр, Фаза 0). В статистике игра делится между жанрами по 1/N. Английские значения нормализуются (SIMULATOR=SIMULATION, UNIQUE → «Другое»), нужен словарь RU-подписей.
- NPSSO от технического аккаунта. Refresh token живёт ~10 дней (проверено в Фазе 0), срок самого NPSSO не измерен. Синк должен идти чаще раз в 10 дней, нужен индикатор и процесс обновления. В PSN 214 игр (не 169). Секреты только на сервере.
- Темы: Night (по умолчанию), Memory Card, Crystal Towers, Wave, Tiles, Activity, Dark (`data-theme="graphite"`). Одна разметка, меняются значения токенов и несколько декоративных правил темы.

## Стек
- Next.js (App Router) + TypeScript strict, Tailwind + CSS-переменные для токенов тем.
- Postgres (Neon через Vercel) + Drizzle ORM.
- `psn-api` (неофициальная). Доступ к PSN только через `src/server/psn/`.
- Vercel Cron раз в сутки: `/api/cron/sync`, защита `CRON_SECRET`.
- Вход: один пароль `ADMIN_PASSWORD`, подписанная cookie. Весь сайт закрыт. С Фазы 20: вход только по белому списку (способ входа — решение Артёма), `ADMIN_PASSWORD` остаётся аварийным входом владельца.
- Тесты: Vitest (логика, БД на PGlite через `freshPglite()` из `src/db/test-utils/pglite.ts`, не `new PGlite()`), Playwright (e2e). В CI на каждый push в main и PR: lint+typecheck, Vitest, Next build, E2E smoke, полный e2e (chromium desktop+mobile, 4 шарда), проект webkit-iphone (`dialog-scroll.spec.ts`, на `ubuntu-24.04`) и PWA на прод-сборке (`npm run e2e:pwa`, файлы `e2e/pwa-build*.spec.ts`), без retries: флаки чинятся по причине, а не повторами. Артём пользуется iPhone Safari и PWA: правки UI прогонять и на `--project=webkit-iphone`.

## Структура

## Команда агентов
Оркестратор — основная сессия. Артём общается только с ним. Сабагенты в `.claude/agents/`: `designer`, `backend`, `frontend`, `qa`.

Правила оркестратора:
- Работает по `plan.md`, фазами. Фаза закрыта только после приёмки QA.
- Делегирует с брифом: цель, входные файлы, критерии готовности, что не трогать.
- Контракты (схема БД, API, токены) сначала фиксируются в `docs/`, потом реализуются.
- Зоны: designer — `docs/design-system.md` и токены; backend — `src/server`, `src/db`, `src/app/api`; frontend — `src/app` (страницы), `src/ui`; qa — тесты и отчёты. Чужие зоны не трогают.
- Параллелит независимое (например designer и backend в Фазе 0).
- Отвечает Артёму коротко, списками, риски называет прямо.
- Миграции на прод применяет CI (Фаза 46, решение Артёма 2026-11-02), не агент и не SQL Editor. Агент: меняет `src/db/schema.ts`, `npm run db:generate`, коммитит миграцию и тесты; `docs/release-neon-NNNN.sql` и `release-sql-NNNN.test.ts` больше не пишет (старые 0000–0027 остаются историей). На push в main после зелёных проверок job `DB migrate (prod)` применяет миграции сначала на временной ветке Neon от прода, потом на проде; Vercel выкатывает код только после этого check. SQL на ревью — артефакт `migration-plan-<sha>` в прогоне CI. Repo variable `MIGRATIONS_CI=on` включена (2026-11-03, настройка: `docs/release.md` §6). Порядок на push в main: `DB план (прод, только чтение)` → при строке `-- DATA LOSS` ждёт `DB подтверждение потери данных` (environment `production-db-approve`, Approve нажимает только Артём, агент никогда) → `DB migrate (prod)`; этот job — Deployment Check в Vercel, без него деплой не выкатывается. Ручного SQL в Neon SQL Editor больше нет (кроме аварийного пути ниже).
- Правила миграций: только expand (старый код обязан работать на новой схеме: между миграцией и выкатом и при откате кода в Vercel работает старый код). Применённую миграцию не править (CI сверяет sha256 и падает). `when` в журнале строго растёт: при конфликте с main миграцию пересоздать поверх свежего main. Удаление/сужение/переименование — отдельной миграцией после выката кода, с строкой `-- DATA LOSS: <что теряется>` в файле и согласием Артёма (кнопка Approve в GitHub, environment `production-db-approve`). `CREATE INDEX CONCURRENTLY` — только в миграции с `-- migrate:no-transaction`.
- Если CI-миграция упала: прод остаётся на старом коде и старой схеме (миграция в транзакции, деплой не выкатывается). Чинить новой правкой той же неприменённой миграции или новой миграцией; Force Promote в Vercel не нажимать. Аварийный ручной путь (SQL Editor) — только по просьбе Артёма.
- Ветка `main` под ruleset: force-push и удаление ветки запрещены, историю не переписываем; прямые push в main разрешены (после зелёных локальных проверок), PR не обязателен. Настройки Vercel/GitHub (регион, переменные, environments, ruleset) агент не меняет.
- Согласие Артёма нужно на: деплой в прод, миграции с потерей данных, смену секретов, добавление платных сервисов.

## Правила кода
- Без `any` без комментария с причиной.
- `src/ui` не импортирует рантайм из `src/server` (только `import type`). Общие чистые константы и функции (без env/БД/сети), нужные и серверу, и UI, живут в `src/shared/`.
- Ошибка PSN не роняет сайт: показываем последние сохранённые данные и статус синка.
- Синк идемпотентный, каждый запуск пишется в `sync_runs`. Синк разбит на батчи, чтобы уложиться в лимит функции Vercel.
- Не логировать токены и NPSSO. `.env*` в `.gitignore`, в репо только `.env.example`.
- Даты хранить в UTC, показывать в Europe/Moscow.
- Коммиты небольшие, по фазам.
- Имена тестов — по фиче, не по фазе: `e2e/<фича>[-<аспект>].spec.ts`, `src/**/<модуль>[-<аспект>].test.ts`; краевые случаи QA — суффикс `-edge`, снимки — `-shots`. Префиксы `phaseNN-`/`qa-phaseNN-` не заводить; номер фазы/пункта можно писать в заголовке `describe` или в комментарии. Старые имена: `docs/qa/test-renames.md`.
- Скриншоты и PNG: в git не коммитим (`docs/qa/**/*.png` в `.gitignore`). e2e пишут снимки через `shotsDir()` из `e2e/shots.ts` в `test-results/shots/` (артефакт CI) или в `SHOTS_DIR`. Перегенерированные снимки, отладочные файлы и трейсы не коммитить. Исключения: `docs/reference/*.png`, иконки приложения. Подробно: `docs/qa/README.md`.
- Никакого `backdrop-filter` на повторяющихся элементах списков (карточки, строки, чипы в сетке): в WebKit (iPhone Safari/PWA) каждый слой с blur ест память и CPU, длинные списки падают или тормозят. Blur допустим только на единичных оверлеях (шапка, шторка, лоадер).
- Первый экран `/` рендерится на сервере (SSR): данные коллекции приходят в HTML через «тонкий» payload (`loadCollectionInitialSlim` в `src/server/collection/initial.ts`, урезание в `slim.ts`: только поля карточек первого экрана, без тяжёлых полей окна игры), остальное догружает клиент. Раскладку первого экрана выбирает cookie `ps-layout` (`src/shared/layout-hint.ts`; при первом визите без cookie ширину берём по устройству из `Sec-CH-UA-Mobile`/User-Agent, `withDeviceWidth`), чтобы SSR совпадал с клиентом без скачка (CLS 0). Не добавлять в первый экран данные, которых нет в slim-payload, и не ломать совпадение SSR/клиента.
