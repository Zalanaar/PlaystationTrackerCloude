## Что проверено

Оценка часов (`src/server/stats/estimate-qa.test.ts`, новые тесты):
- `estimateByMonth` против эталона без кода продукта (обход по дням, Intl Europe/Moscow): 2000 случайных входов, метки у границ месяца МСК (20:59:59Z / 21:00:00Z), остаток округления, нечётные секунды. Расхождений нет; сумма долей всегда равна S0.
- Покрыты: нет `first_played_at`, он позже D0, `last_played_at` null / раньше first / позже D0, S0=0, один месяц, игра добавлена после первого синка (свой D0), 13+ месяцев через границу года.
- Нет двойного счёта: для 120 случайных игр сумма секунд по всем годам 2018..2027 равна S_last (с оценкой) или S_last - S0 (без оценки), точно. Месяцы по отдельности суммируются в то же число. Месяц D0: доля оценки + реальные после D0, без дублей.
- Сумма `byMonth` за год совпадает с `header.hours` с точностью до округления (не более 0.7 ч на 12 месяцев); `estimatedByMonth <= byMonth`.
- Статистика и Итоги (PGlite, 40 игр, ~5 тыс. снимков, 7 лет): `hours.total`, `byMonth`, `estimatedByMonth`, `estimatedHours`, `hasEstimate`, `firstSnapshotDate` идентичны за каждый год. `years[].hasData` Итогов совпадает с `mode` (кроме BUG-E1); каждый год Итогов с данными есть в `years` Статистики.
- Соседние места: жанры (игра только с оценкой в периоде учитывается, без оценки и без часов нет, оценка в 2025 не создаёт жанры в 2026); топ-игры и самая долгая считаются по часам года с оценкой (`estimated`), сверка с SQL есть и у разработчика; `service`-игры считаются в часах, в пройдено/брошено не попадают.

Статус `service` (`src/server/collection/service-qa.test.ts`):
- Миграция 0001 применяется на пустую БД и на БД с данными из 0000: старые строки целы, до миграции `service` недоступен, после доступен, порядок enum верный; штатный drizzle-migrator идемпотентен.
- CHECK: у `service` нельзя хранить `completed_at`/`dropped_at`.
- Смены completed -> service -> dropped -> service -> null: даты ставятся/обнуляются, повтор не трогает `status_changed_at`, правка даты у service = `date_not_allowed`.
- Bulk: смесь статусов, `changed` не считает уже `service`, дат не остаётся.
- `summary.services`: 60 игр -> 50, порядок `last_played desc nulls last, title, id`, `counts.service = 60`; `/api/games?status=service` отдаёт все 60 и `total = 60`. UI (блок грузит `/api/games`, `summary.services` не читает) расхождения счётчика и списка не даёт; предел только 300 карточек (лимит API).
- `continue` включает `service` (по контракту 9.3), исключает completed/dropped и игры без запуска. В UI поле `continue` не используется.

UI (`e2e/service-qa.spec.ts`, снимки 320/360/390 x Night/Graphite/Activity в `SHOTS_DIR`): блок сервисов (120 игр, длинные названия): внутри блока нет выходов за экран, кнопка «Показать ещё/Свернуть» в экране и не ниже 40px, список на 320 с обрезкой названий; столбцы real/est с полосами и пунктиром, легенда, плашка, «≈» в шапке, подсказка по тапу на 320/360/390. Просмотр снимков: блок и столбцы читаемы, ромб виден, оценочные столбцы отличаются не только цветом. Разработческие `service.spec.ts`, `stats.spec.ts`, `wrapped.spec.ts` проходят.

## Нестабильный npm test: причина

Тест не один: PGlite (WASM) стартует 1-8 с на файл при ~35 параллельных воркерах (4 ядра). На холодном кэше или при нагрузке `beforeAll` с `createTestDb()` превышает дефолтный `hookTimeout` 10 с (и `testTimeout` 5 с у тяжёлых случайных тестов). Падают разные файлы (`collection/query.test.ts`, `sync/qa-phase2.test.ts`, `stats/query-sql.test.ts`), логика не виновата. Воспроизведено 3 из 3 при трёх параллельных `vitest run`. Исправлено в `vitest.config.ts`: `testTimeout 30000`, `hookTimeout 60000`; после правки 3 из 3 параллельных прогонов зелёные.

## Риски

- Оценка равномерна по месяцам по контракту: если игрок играл только в первый месяц диапазона, графики до первого синка будут ровными «столбцами оценки». Продукт это показывает пометкой, но в Итогах «самый активный месяц» (`topMonth`) для прошлых лет определяется оценкой, а не фактом.
- `years` Итогов считает реальные дельты запросом с `lag` по всем снимкам и грузит все игры для жанров на каждый запрос (как в Фазе 6, к ним добавился `getEstimateInputs` по всем играм): на Neon HTTP замера нет.
- Игры-сервисы: UI грузит не более 300 игр статуса `service` (`FULL_LIMIT`); при большем числе счётчик больше списка (кнопка «ещё» ведёт на догрузку). Для одного пользователя нереально, но граница есть. `summary.services` (до 50) клиентом не используется, поле мёртвое.
- В Разборе на мобильном нет кнопки «Сервис» в нижней строке (`MOBILE_KEYS` без `service`); доступна через меню статуса. Соответствует описанию в design-system §3 («в sheet»), но в быстром режиме свайпов сервис не выставить.
- Миграция 0001 (`ALTER TYPE ... ADD VALUE`) проверена на PGlite; на реальном Neon не прогонялась. На Postgres 12+ она допустима в транзакции, пока значение не используется в той же транзакции (здесь не используется).
- Если dev-сервер выдаёт `.next` чужого запуска, e2e может быть нестабильным; в моих прогонах нет.

## Не проверено

- Реальная БД Neon и реальные данные Артёма; HTTP-роуты `/api/stats`, `/api/wrapped` с настоящей сессией (только функции с PGlite и моки в e2e).
- Тема Activity/Graphite на слайдах Итогов с оценкой: смотрелись только выборочные снимки статистики; слайд «Часы» с оценкой проверен разработческим e2e, глазами не пересматривался.
- iOS Safari и физические устройства (только эмуляция Chromium, Pixel 7 + принудительные ширины).
- 4 из 7 тем референса не существуют в проекте (три темы).
