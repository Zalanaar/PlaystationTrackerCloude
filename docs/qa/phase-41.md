# QA Фазы 41: несколько профилей PSN у одного входа

Ветка `claude/phase-41-psn-profiles`. Критерии: plan.md «Фаза 41», контракт `docs/api-contract.md` «Фаза 41», спека `docs/design-system.md` §17.

## Вердикт: НЕ ПРИНЯТО (условно: принять после правки QA-41-1 и QA-41-3)

Серверная часть (изоляция, IDOR, подмена pid, лимиты, архив, cron) в порядке. Блокируют два дефекта клиента: вход member уходит в онбординг после добавления профиля (QA-41-1) и шапка на телефоне не помещается при 2+ профилях (QA-41-3).

## Дефекты

### QA-41-1 (High): профиль, добавленный member-входом, уходит на `/onboarding`
Шаги: вход member (друг, не owner) -> «Профили PSN» -> «Добавить PSN-профиль» с галкой «Сразу открыть» -> ник проверен (`accessStatus: ok`).
Факт: `POST /api/me/profiles` создаёт строку с `onboarded_at = NULL` (`src/server/auth/profiles.ts`, insert ~стр. 224). `redirectToOnboardingIfNeeded` (`src/app/(app)/onboarding-guard.ts`) берёт роль из cookie (роль входа = member) и вызывает `needsOnboarding` по `GET /api/me/psn` активного профиля: ник есть, `onboardedAt` null -> редирект на `/onboarding` при любой навигации (guard в layout всей группы `(app)`, включая `/profiles`). Выйти на основной профиль или отвязать этот можно только пройдя онбординг (первый синк).
Для owner-входа не воспроизводится: роль cookie = owner, guard выходит сразу (тест `qa-onboarding.test.ts`, первый кейс зелёный). Профиль «добавлен владельцем с role=member в строке» риска не несёт.
Тест: `src/app/api/me/profiles/qa-onboarding.test.ts`, `it.fails` (станет красным после починки: заменить на `it`).
Фикс (backend): при создании и восстановлении профиля с `accessStatus = 'ok'` ставить `onboarded_at = now()` (ник проверен, дальше синк по cron или кнопкой). Дополнительно (frontend/backend): guard не должен требовать онбординг для дополнительного профиля вообще (`profile.primary_user_id IS NOT NULL`); если пустой профиль без первого синка, показывать на Коллекции пустое состояние с «Синхронизировать».

### QA-41-2 (Medium): после смены профиля фокус не переходит на h1
Шаги: два профиля -> выбрать другой в переключателе (или «Добавить» с галкой «Сразу открыть»).
Факт: `document.activeElement` остаётся `body`. `focusPageHeading()` в `PsnProfileProvider.tsx` вызывается сразу после `setSwitching(null)`, пока `html[data-psw]` ещё стоит (`.ps-main { visibility: hidden }`, `profiles.css:10`), и `focus()` на скрытом элементе молча не срабатывает; повторной попытки нет (цикл повторов только на случай «h1 ещё нет»).
Фикс (frontend): фокусировать после снятия `data-psw` (в `useEffect` на `switching === null`) или повторять, пока `document.activeElement !== h1` (до ~1,5 с).
Тест: `phase41-profiles.spec.ts` «фокус на h1 после смены профиля (QA-41-2)», `test.fail` (после фикса станет «неожиданно зелёным», снять `test.fail`).

### QA-41-3 (High): шапка не помещается на телефоне при 2+ профилях
Шаги: 2+ профиля, вьюпорт 320, 360, 390, 412 px (замер): правая группа шапки `.ps-header__right` заканчивается на 434, 443, 450, 451 px (за краем экрана на 80-115 px). Чип профиля обрезан, иконки справа (меню/аватар) недоступны; горизонтального скролла нет (скрыт), поэтому дефект тихий. Снимок: `docs/qa/shots-41/profiles-night-360.png`. При одном профиле шапка помещается.
Фикс (designer/frontend): на `<= 480 px` чип показывает только инициал-аватар без текста ника (ник в `aria-label` и в листе), либо `max-width` ~ 96 px с `text-overflow: ellipsis` и `min-width: 0` у блока статуса синка (он должен сжиматься первым). Проверить 320, 360, 412 и длинный ник из 16 символов, 7 тем.

### QA-41-4 (Low): косметика
- «Что нового»/полоса «С прошлого визита» берут `id` из `/api/auth/me` (теперь id активного профиля), поэтому «прочитано» и «скрыть до 00:00» хранятся отдельно у каждого профиля. Не ошибка, но поведение стоит зафиксировать в контракте.
- На 360 px текст синка в шапке усечён («Синк: 5 дн. на…») и сильнее, чем до Фазы 41 (старая заметка плана для 320 px).

## Проверено без замечаний

- Переключатель: в DOM только при 2+ профилях; меню (десктоп), лист (мобильный); ArrowDown/Escape; повторный выбор того же профиля не шлёт запрос; ошибка смены -> тост «Повторить»; 401 -> `/login`.
- Смена: завеса «Открываю профиль …» видна, `data-psw` и `visibility: hidden` на контенте; после неё в `main` только игры нового профиля (прежних нет); тост «Профиль PSN: …».
- Добавление: все коды `invalid_request`, `profile_limit`, `user_limit`, `psn_id_taken`, `psn_not_found`, `psn_private`, `rate_limited` (таймер в кнопке, `Добавить (N)`), `psn_unavailable` («Повторить»), сеть, неизвестная 500; форма остаётся открытой; формат ника блокирует кнопку.
- Лимит 3 из 3: «Добавить» отключена, причина текстом; пустое состояние при одном профиле.
- Отвязка: кнопка включается только при точном нике (регистр и пробелы игнорируются), архив с «удалится через 30 дней», «Вернуть» (3 из 3 снова), «Удалить сразу» с подтверждением, ошибки `confirm_mismatch`, `sync_in_progress`, `not_found`, отвязка активного профиля -> открывается основной.
- localStorage: ключи вида `ps-view:{id}`, у второго профиля настройки первого не наследуются, общий ключ не создаётся.
- Безопасность (живой dev-сервер + PGlite): без cookie 401 на всех роутах профилей и редирект `/profiles` на `/login`; cookie с изменённым `pid` без пересчёта подписи, подпись чужим секретом, `pid` = 0, -5, 1.5, "2" -> 401; валидно подписанный `pid` при недоступной БД не даёт 200; `pid` в query не влияет; IDOR, чужой/архивный профиль -> одинаковый 404, лимиты и гонки, смена профиля не продлевает срок — тесты `routes.test.ts`, `session-profiles.test.ts`, `profile-isolation.test.ts` зелёные. Service worker: `/api/*`, POST и RSC обходит, `/profiles` только сеть (при отказе `/offline`), в кэш не кладётся; `public/sw.js` фазой не менялся. В новом коде нет `console.*`, токены и NPSSO в ответах профилей не отдаются.
- Подмена данных между входами: в тестах два входа по два профиля, коллекция/трофеи/копии не пересекаются.

## Ночная цепочка синка: замер

Стенд: PGlite, движок PSN заменён заглушкой, 6 профилей (2 входа по 3). Результат: 6 запусков `daily`, у каждого свой `sync_runs`, порядок по `id`, цепочка `?queue=<id>` дошла до конца сама; накладные расходы оркестрации около 85 мс на всё (14 мс на профиль), то есть пренебрежимы.
Реальное время определяет PSN, живьём не измерялось. Оценка по контракту (8.4 и 41.4): обычный день один профиль = одно звено до `SYNC_TIME_BUDGET_MS` (50 с, обычно 20-40 с) -> 6 профилей около 3-5 минут; первый синк нового профиля около 3 звеньев (2-2,5 минуты) плюс 1-2 суток на цвета обложек. Лимит функции Vercel (60 с) от числа профилей не зависит: каждое звено — отдельный вызов. Вывод: ночное окно не проблема (укладывается в 10 минут при 6 профилях); растёт число обращений к PSN под одним NPSSO, параллели нет. Риск: обход держится на цепочке самовызовов, сбой одного вызова (сеть, холодный старт) обрывает хвост очереди до завтра; watchdog `sync_missed` это увидит.
