## Баги и замечания

**QA-32-1 (средняя). Шапка `docs/release-neon-0022.sql` неверна, выкат кода до миграции ломает весь План.**
Шапка: «новый код на старой схеме: цель отвечает 503, остальной план работает». Факт: Drizzle `select()` из `roadmap_settings` включает `goal_mode`/`goal_count`, поэтому на схеме без 0022 падают `getSettings` и `getGoal`, то есть `GET /api/roadmap` целиком (`getGoal` в общем `Promise.all`), настройки плана, экспорт резервной копии (watchdog отдаёт `backup: error`). Воспроизведение: `src/server/roadmap/qa-old-schema.test.ts` (схема после 0021). Порядок «сначала SQL, потом деплой» обязателен; шапку исправить (backend), в релизных заметках Артёму сказать прямо.

**QA-32-2 (низкая, исправлено QA). `e2e/phase11-backlog.spec.ts` ждал «—» у игры без часов с проверенным HLTB.** По спеке состояние C теперь «нет на HLTB» без прочерка. Ожидание заменено на `нет на HLTB`. Frontend тест не обновил.

**QA-32-3 (низкая). Минимум 15% определяется по `progress >= 0.85`, это даёт ложные срабатывания.** `progress` округляется до 0.01, поэтому наиграно 84.6% базы (реальный остаток 15.4%) даёт progress 0.85 и пометку «мин. 15%» с подсказкой «Игра идёт дольше оценки HLTB». Тест-фиксация в `goal-qa.test.ts`. Рекомендация: backend отдаёт флаг `remainingIsMinimum` (в спеке он был), либо UI сравнивает `remainingHours` с `0.15 * hours`.

**QA-32-4 (низкая, тест). Падающий `watchdog/users.test.ts` «еженедельная копия» связан с фазой, это не «известный посторонний» сбой.** На 830c68b и на ae17eba тест зелёный, с 8d2ed61 красный. Причина: тест поднимает схему `migrations: 15`, а `buildBackup` делает `select()` из `roadmap_settings`, где теперь есть `goal_*`, и получает ошибку колонки (`backup: error`). С `migrations: 23` этот тест зеленеет, но падает соседний («просрочка у нескольких пользователей»), значит фикстуру нужно чинить аккуратно (backend). Продукту в проде (после 0022) не мешает.

**QA-32-5 (низкая). Резервная копия не включает цель года** (`backup/export.ts`, формат `roadmapSettings: { year, hoursPerWeek }`). После восстановления цель теряется. Решить: включить в формат или явно зафиксировать в контракте 20.

**QA-32-6 (низкая, по спеке). Состояние `no_data` в UI** (порог «меньше 2 завершённых игр») скрывает `ahead/behind` от backend, хотя контракт отдаёт статус уже при одном завершении. Допустимо (в спеке вопрос 2), но порог живёт только во frontend; для `backlog_to` число завершений восстанавливается обратным пересчётом из темпа (`completedInYear`), с ошибкой округления. Лучше отдавать `completedInYear` с backend.

**QA-32-7 (информационное). Отклонения frontend от спеки, оценка критичности.**
- `minimum` по `progress >= 0.85`: см. QA-32-3, низкая.
- Состояние G (мало данных) и порог 2: QA-32-6, низкая.
- `planToday` (засечка «где должен быть») не показывается, потому что backend не отдаёт `startBacklog`/`planToday`; полоса `backlog_to` = N / текущий, а не доля сокращения от старта (открытый вопрос 1 спеки). Низкая, смысл полосы в этом режиме слабее.
- Статусы цели соответствуют контракту (`achieved/ahead/onTrack/behind/not_started` + `no_data`, прошлый и будущий год). Критичного нет.
- Для прошлого года `backlog_to` считает бэклог «сейчас», а не на конец того года (особенность контракта 17.3a): информационное.
