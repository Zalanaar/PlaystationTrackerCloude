# PSN API: результаты Фазы 0

Статус: **проба на реальных данных выполнена** (2026-10-27), итоги в разделе «Результаты запуска». Разделы «Что должно быть доступно» и «Что, вероятно, недоступно» написаны до запуска (по типам `psn-api@2.18.1`); где они расходятся с результатами, верны результаты.

## Как запустить пробу
1. Скопировать `.env.example` в `.env`, заполнить `PSN_NPSSO` и `PSN_TARGET_ONLINE_ID`.
2. `npm install`, затем `npm run psn:probe`.
3. Скрипт печатает только агрегаты (счётчики, ключи полей, диапазоны дат), токены и NPSSO не выводит. Результат внести в раздел «Результаты запуска» ниже.

Получение NPSSO: войти в аккаунт PlayStation в браузере, затем открыть `https://ca.account.sony.com/api/v1/ssocookie` и взять значение поля `npsso` (64 символа). Использовать технический аккаунт.

Требование доступа: технический аккаунт должен видеть целевой аккаунт: быть у него в друзьях, а у цели список игр и трофеи должны быть открыты для друзей. Иначе будет ошибка доступа или пустой ответ.

## Что должно быть доступно (по типам библиотеки, не подтверждено запросом)
| Данные | Метод `psn-api` | Поля |
|---|---|---|
| Авторизация | `exchangeNpssoForAccessCode` -> `exchangeAccessCodeForAuthTokens` -> `exchangeRefreshTokenForAuthTokens` | access token (~1 час), refresh token (~2 месяца по доке библиотеки) |
| accountId по нику | `getProfileFromUserName` | `profile.accountId` |
| Игры и часы | `getUserPlayedGames(auth, accountId)` | `titleId`, `name`, `category` (ps4_game/ps5_native_game/pspc_game), `playCount`, `playDuration` (ISO 8601, напр. `PT228H56M33S`), `firstPlayedDateTime`, `lastPlayedDateTime`, `imageUrl`, `concept.{id,titleIds,name,media}`, `service` |
| Обложки | там же | `imageUrl`, `concept.media.images[]` (url, type, format), `media.screenshotUrl` |
| Дата последнего запуска | там же | `lastPlayedDateTime` |
| Трофейные тайтлы | `getUserTitles` | `npCommunicationId`, `npServiceName`, `trophyTitleName`, `progress`, `earnedTrophies`, `definedTrophies`, `lastUpdatedDateTime` |
| Трофеи с датами | `getUserTrophiesEarnedForTitle(..., "all", {npServiceName})` | `earned`, `earnedDateTime`, `trophyType`, `trophyRare`, `trophyEarnedRate` |
| Названия трофеев | `getTitleTrophies` | имя, описание, иконка |

## Что, вероятно, недоступно
- **История часов**: только суммарный `playDuration`. Часы за период только по нашим ежедневным снимкам (уже решение проекта).
- **Жанры**: в типах `getUserPlayedGames` поля жанра нет. Возможно, `concept` содержит `genres` в реальном ответе (в типах не заявлено); проба печатает `concept.genres`, если оно есть, и долю игр с жанрами.
- **Связь игры с трофейным тайтлом**: `titleId` (CUSA/PPSA) и `npCommunicationId` (NPWR) разные идентификаторы. Прямой связи в ответах нет, придётся сопоставлять по названию (риск неточностей: ремастеры, DLC, PS4/PS5 версии). Проверить пробой.
- **Игры без трофеев**: их нет в `getUserTitles`, но есть в played games.
- Статуса «пройдено» PSN не отдаёт (решение проекта: ручные статусы).

## Лимиты
Официальных лимитов нет (API неофициальный). Известно из практики и доков библиотеки: ответ 429 при частых запросах, окно порядка 300 запросов за 15 минут (не подтверждено). Проба делает 30 быстрых запросов и фиксирует первую ошибку. Рекомендация для синка: пауза 300+ мс между запросами, повтор с backoff на 429/5xx, батчи.
Пагинация: `getUserPlayedGames` limit до 200 за страницу, `getUserTitles` до 800.

## Риски
- Библиотека неофициальная и может сломаться, использование может нарушать ToS Sony: изолировать в `src/server/psn/`.
- NPSSO живёт около 2 месяцев; refresh token даёт продление, но при его протухании нужен новый NPSSO. Нужен индикатор на сайте.
- Часы чужого аккаунта: **подтверждено пробой, доступны** (`getUserPlayedGames`). Остаточный риск: смена приватности цели.

### Сопоставление игры с трофейным тайтлом
Прямой связи в getUserPlayedGames нет (`titleId` CUSA/PPSA против `npCommunicationId` NPWR). Но есть эндпоинт `getUserTrophiesForSpecificTitle(auth, accountId, { npTitleIds })`: до 5 titleId за запрос (больше даёт Bad Request). Ответ: `titles[{ npTitleId, trophyTitles[] }]`, в trophyTitles есть npCommunicationId и npServiceName.

Результат на данных (214 игр):
- По titleId сопоставлено **162/214 (76%)**, все 162 сета есть в getUserTitles. У 6 игр несколько сетов: связь нужна многие-ко-многим.
- Обратное покрытие: из 170 трофейных тайтлов **169 (99,4%)** привязаны к игре по titleId; 1 сиротский сет.
- 52 игры без сета по titleId: у 3 есть сиблинг того же concept.id с сетом (другая платформенная версия), у 49 сета нет. Вероятная причина: трофеи для них не синхронизированы или не получены (getUserTitles отдаёт только тайтлы с трофеями на аккаунте). Среди них крупные игры с заведомо существующими трофеями, так что причина не доказана. Это отсутствие данных в PSN, а не ошибка сопоставления.
- Сопоставление по имени ненадёжно: из 52 сработало у 3 (расхождения ™/®, «PS4 & PS5», Edition). Только последний fallback.

Алгоритм (в `src/server/psn/`, результат в таблице связи game <-> trophy_title):
1. Для каждой новой игры батчами по 5 вызвать getUserTrophiesForSpecificTitle, сохранить все npCommunicationId (1..N), источник `titleId`.
2. Нет сета, но у другого titleId того же concept.id он есть: наследовать (источник `concept`).
3. Иначе игра без трофейных данных (`trophy_set = null`); перепроверять при каждом полном синке, трофеи могут появиться.
4. Fallback по нормализованному имени (нижний регистр, без ™®, пунктуации, Edition/PS4/PS5) только для сиротских сетов, источник `name`, с ручной правкой.
5. Сеты без игры не терять: хранить, учитывать в трофеях по earned_at.
Стоимость: 43 запроса на первый синк (214 игр), потом только новые игры.

### Риски (обновлено)
- Часы чужого аккаунта: **закрыто, доступны**. Остаточный риск: смена приватности цели; тогда синк получает ошибку доступа, данные не стираем.
- Refresh token ~10 дней: синк раз в сутки должен обновлять пару токенов (exchangeRefreshTokenForAuthTokens) и сохранять новый refresh в БД (не логировать). Простой синка >10 дней или протухший NPSSO: нужен новый NPSSO, индикатор на сайте. Срок жизни самого NPSSO пробой не проверялся.
- 49 игр без трофейных данных: в трофеях и прогрессе не учитывать, показывать «нет данных».
- Не-игры (6 тайтлов): оставлять category ps4_game, ps5_native_game, pspc_game. UI показывает 169 игр против 214 в PSN; расхождение (вероятно, фильтр прототипа) уточнить у frontend.
- Лимиты не найдены; оставить паузу 300 мс и backoff на 429/5xx.
- Библиотека неофициальная: держать изоляцию и сохранённые JSON-образцы для тестов маппинга.

### Поведение psn-api 2.18.1, важное для синка (Фаза 2, по исходникам библиотеки, не по живым ответам)
- Библиотека вызывает глобальный `fetch` и сразу `.json()`: **HTTP-статус наружу не отдаётся**. Ошибки приходят как `Error` с текстом из `error.message` ответа; не-JSON тело (например «Too Many Requests» или HTML 5xx) даёт `SyntaxError`, текст которого содержит начало тела. Классификация (429/доступ/401/5xx) поэтому идёт по тексту и **не проверена на живых ошибках**: см. `src/server/psn/errors.ts`.
- `exchangeRefreshTokenForAuthTokens` и `exchangeAccessCodeForAuthTokens` **не бросают** при отказе, а возвращают объект с `undefined` полями. Код проверяет наличие токенов явно.
- `exchangeNpssoForAccessCode` при отказе бросает ошибку с «NPSSO».
- `getUserPlayedGames` в типах не знает `concept.genres`; маппинг читает поле защитно.

### Баннер игры и профиль (Фаза 9)
Проверено по фикстурам `src/server/psn/__fixtures__/played-games.json` и типам psn-api 2.18.1. Живых ответов с NPSSO в этой сессии не было, поэтому реальное распределение типов не измерено (см. риск ниже).
- Элемент `concept.media.images[]` содержит только `url`, `format` (в примерах `UNKNOWN`) и `type`. **Ширины и высоты нет**, поэтому условие контракта 12.1 «`width > height`» применимо только как запасное, если PSN их когда-нибудь добавит.
- В фикстурах и в доке библиотеки встречается один тип: `FOUR_BY_THREE_BANNER`. В 6 из 7 фикстурных тайтлов `images` пуст; у `ps5_native_media_app` тоже. Из знания публичных PS Store-типов добавлены остальные (не подтверждены живыми данными): `SIXTEEN_BY_NINE_BANNER`, `GAMEHUB_COVER_ART`, `BACKGROUND`, `SCREENSHOT`; квадрат и вертикаль (`MASTER`, `LOGO`, `PORTRAIT_BANNER`, иконки) не годятся.
- Правило (`pickBanner` в `src/server/psn/mapping.ts`): первое изображение по приоритету типов `SIXTEEN_BY_NINE_BANNER`, `GAMEHUB_COVER_ART`, `FOUR_BY_THREE_BANNER`, `BACKGROUND`, `SCREENSHOT`; иначе любое с числовыми `width > height`; иначе `null`. Синк пишет `coalesce(новое, старое)`.
- Профиль: `getProfileFromUserName` отдаёт `avatarUrls[{size, avatarUrl}]` (размеры `xs..xl`; берём самый крупный по `size`) и `trophySummary {level, progress, earnedTrophies}`. Поле `tier` в типах библиотеки не объявлено; читается защитно, при отсутствии `null`. Любое отсутствующее поле даёт `null`, прежнее значение в БД не затирается.
- **Аватар (Этап 5, 17.1, `avatarUrl=null` на проде).** Вероятная причина: `profile2` отдаёт адреса аватара по `http://static-resource.np.community.playstation.net/...`, а правка BUG-P9-2 (`httpsUrl`) отбрасывала всё, кроме `https:`. Исправление: `psnAvatarUrl` повышает `http` до `https` на хостах `*.playstation.net` и `*.playstation.com`, остальные не-https адреса по-прежнему отбрасываются. НЕ проверено на живом ответе (нет NPSSO в окружении): если после синка `profile.avatarUrl` всё ещё `null`, значит PSN не отдаёт `avatarUrls` для этого аккаунта (ограничение приватности или другой формат), и нужен дамп `profile.avatarUrls` без токенов. Прежнее значение в БД не затирается пустым.
- Риск: если у реальных игр `images` пуст или типы отличаются, баннер будет `null` у большинства игр (UI рисует размытую обложку). После первого синка проверить `select count(banner_url), count(*) from games`.

## Фаза 12: каталог новинок (RAWG) и PS Store

### PS Store через `psn-api`
Каталога PlayStation Store в `psn-api` нет. Библиотека покрывает: авторизацию (NPSSO -> access/refresh), профиль, библиотеку игр пользователя (`getUserPlayedGames`), трофеи и их группы, друзей/сообщения. Поиска по магазину, дат релиза, цен и обложек невышедших игр нет, поэтому для невышедших игр PSN не источник. Обложки и даты берутся из внешнего каталога или вводятся вручную. (Проверено по списку экспортов и типам библиотеки версии 2.18; живого запроса к магазину не делалось, и неофициальные веб-эндпоинты магазина мы не используем: ToS и хрупкость.)

### RAWG (rawg.io/apidocs)
- Выбран как основной внешний каталог (решение Артёма): один бесплатный ключ `RAWG_API_KEY` (только сервер), поиск по названию, дата выхода, обложка, платформы.
- Запрос: `GET https://api.rawg.io/api/games?key=<KEY>&search=<q>&page_size=10`. Ответ: `{ count, next, previous, results: [ { id, slug, name, released: "YYYY-MM-DD" | null, tba, background_image, platforms: [ { platform: { id, name, slug } } ] | null, ... } ] }`. Клиент берёт только `id`, `name`, `released`, `tba`, `background_image`, `platforms[].platform.{name,slug}`.
- НЕ проверено вживую (в среде нет ключа): точные поля сверены с публичной документацией RAWG и пишутся оборонительно. Первый ручной прогон с ключом: `GET /api/roadmap/catalog/search?q=hades` под сессией. Если форма ответа отличается, клиент отвечает `503 catalog_unavailable` с `details.reason = "bad_response"`, а не пустым списком.
- Условия использования: на экране, где показываются данные RAWG, нужна активная ссылка на RAWG (frontend). По публикуемым данным лимит бесплатного плана около 20 тыс. запросов в месяц (сторонние источники, не проверено); для одного пользователя с поиском по кнопке этого достаточно, кэш не нужен.
- Даты анонсов в RAWG менее точны, чем в IGDB: это подсказка, дата правится вручную. Если RAWG окажется неточным, запасной вариант IGDB (Twitch client id/secret, токен раз в ~60 дней), клиент вынесен в `src/server/catalog/` и заменяется без изменения API (`CatalogCandidate`).
- Обложки отдаются с `media.rawg.io` по https; хранится только URL (`planned_games.cover_url`), картинка не копируется. Хост нужно разрешить в `next/image`, если frontend использует его.

## Этап 5: что PSN и HLTB не дают (честно)
- Дату «пройдено» PSN не отдаёт (только суммарные часы и дату последнего запуска), поэтому резервная копия (контракт 20.3) хранит ручные `completed_at`/`dropped_at`: из PSN они не восстановимы.
- Копия разметки намеренно не содержит игры, часы, снимки и трофеи: всё это приходит из PSN и пересоздаётся синком. Восстановление сопоставляет игры по `title_id`; игра, которой нет в БД (ещё не синхронизирована), пропускается и показывается в `missing`.
- Расход LLM: бесплатные лимиты провайдеров (Groq, Gemini) мы не измеряли; потолки (`LLM_DAILY_LIMIT`, виды вызовов в `src/server/recommend/budget.ts`) это наши предохранители, а не лимиты провайдера. Реальный Groq на пачке из 16 фраз и на 12 играх «Нового от ИИ» с `max_tokens` 3000/4000 не прогонялся (проверить на проде после деплоя: `sync_runs.warnings`, `llmReason`).
